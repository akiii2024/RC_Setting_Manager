# リファクタリング調査結果

更新日: 2026-08-19

## 方針

この文書は、全体リファクタリング中に見つかった不具合候補と運用上のリスク、および修正結果を記録するものです。RF-01〜06は2026-08-19の変更ですべて修正済みです。重要度は、データ消失・ユーザー影響・発生可能性を合わせた評価です。

## RF-01: オフライン固定状態と保存済みオンライン状態が一致しない

- **重要度:** 中
- **根拠:** `app/app_bootstrap.dart` は `preferredOnline = false` として常にオフライン画面を構築します。一方、`SettingsProvider` は同じ `online_mode` キーを読み込み、値が `true` ならクラウドリポジトリの生成を試みます。`AppModeProvider` と `SettingsProvider` が別々に同じ設定を管理しています。
- **想定影響:** 画面はオフラインでも `SettingsProvider.isOnlineMode` が `true` になり得ます。Firebase未初期化時の例外ログ、クラウド保存判定の不整合、オンライン機能再公開時の予期しない同期につながる可能性があります。
- **再現条件:** `SharedPreferences` の `online_mode` を `true` にした状態で現在のオフライン専用リリースを起動し、両Providerの状態を比較します。
- **推奨対応:** オンライン状態の唯一の所有者を決め、`SettingsProvider` へ明示的に注入します。オフライン専用リリースでは保存値を無効化するのか、読み込むが同期しないのかを移行仕様として決定します。
- **今回の状態:** 修正済み。`AppModeProvider.isOnlineActive` を実効オンライン状態の唯一の判定元とし、`SettingsProvider` へ明示注入しました。オフライン専用リリースでは実効状態を常に `false` とし、保存済み `online_mode=true` は読み替え・上書きせず保持します。クラウドリポジトリはオンラインが実効化された操作でだけ遅延生成します。

## RF-02: ローカル永続化失敗が呼び出し元へ伝わらない

- **重要度:** 高
- **根拠:** `SettingsProvider` の `_saveSettings`、`_saveRunLogs`、`_saveOwnedParts`、`_saveCars` などは例外をログへ出した後に正常終了します。CRUD処理は先にメモリを更新し、そのまま通知または成功値を返します。
- **想定影響:** 画面では保存済みに見えても、再起動すると変更が消える可能性があります。容量不足、ブラウザストレージ拒否、破損データなどで発生してもユーザーへ通知されません。
- **再現条件:** 書き込み時に例外を投げる `SettingsLocalRepository` を注入し、`addSetting` を実行します。追加設定はメモリに残り、メソッドも成功値を返します。この現行特性はテストで記録済みです。
- **推奨対応:** 保存結果を型で返し、UIへ失敗状態を通知します。操作単位でメモリ変更をロールバックするか、未保存キューと再試行方針を導入します。
- **今回の状態:** 修正済み。`SettingsSnapshotV2` を `settings_state_v2` の単一キーへ保存し、全変更APIは `SettingsOperationResult<T>` を返します。操作は直列化されたドラフト上で構築し、完全なスナップショット保存成功後にだけライブ状態へ反映します。例外と `setString=false` は失敗結果または起動失敗となり、状態・通知は変更しません。ローカル成功後のクラウド失敗は状態を維持し、`SettingsSyncWarning` を返します。

## RF-03: 車両CRUDで通知とクラウド保存が重複する

- **重要度:** 中
- **根拠:** `_persistCars` がローカル保存、クラウド保存、`notifyListeners()` を実行した後、`updateCar`、`addCar`、`deleteCar` が再度クラウド保存と通知を実行します。
- **想定影響:** オンライン時に同一内容が二重送信され、Firestore使用量と待ち時間が増えます。画面も一操作で複数回再構築され、将来リスナーへ副作用を追加した場合は二重実行の原因になります。
- **再現条件:** 呼び出し回数を記録する `SettingsCloudRepository` とProviderリスナーを注入し、車両の追加・更新・削除を1回実行します。
- **推奨対応:** 永続化と通知を `_persistCars` に一本化し、公開CRUD側の重複ブロックを削除します。先に通知回数を受け入れ基準として確定します。
- **今回の状態:** 修正済み。車両の追加・更新・削除を共通の原子コミットへ統一し、各操作をローカル保存1回、クラウド保存1回、通知1回としました。車種固有項目の更新に伴う表示設定更新と、削除時の表示設定除去も同じローカルスナップショットに含めます。

## RF-04: 走行ログと派生セッティングの保存が一体化されていない

- **重要度:** 中
- **根拠:** `addRunLog` は変更点がある場合に先に `addSetting` を完了させ、その後で走行ログを生成・保存します。ローカル保存とクラウド保存もエンティティごとに独立しています。
- **想定影響:** 途中の保存だけが失敗すると、走行ログから参照されない派生セッティング、またはクラウド側だけ欠けた関連データが残る可能性があります。
- **再現条件:** 派生セッティング保存は成功し、走行ログ保存だけ失敗するリポジトリを使って、変更点付きの走行ログを追加します。
- **推奨対応:** 走行ログと派生セッティングを1つのユースケース結果として構築し、ローカルでは一括コミット、クラウドではバッチまたは再同期可能な処理単位にします。
- **今回の状態:** 修正済み。走行ログと派生セッティングを同じドラフトで生成し、ローカルでは1つのv2スナップショットとして保存します。Firestoreでは `WriteBatch` 1回で両ドキュメントを書き込み、片方だけが確定する経路をなくしました。ローカル失敗時は両方を破棄し、クラウド失敗時はローカル確定を維持して同期警告を返します。

## RF-05: 起動失敗時のRetryがアプリ全体を再度 `runApp` する

- **重要度:** 中
- **根拠:** 起動失敗画面のRetryは `bootstrapApplication()` を再実行し、依存Providerを作り直して `runApp` を再度呼びます。これは元の `main()` 再呼び出しを分離後も維持したものです。
- **想定影響:** 初回起動の非同期処理が残っている場合、再初期化処理と競合する可能性があります。根本原因が継続している場合は、状態を失いながら同じ失敗を繰り返します。
- **再現条件:** `MyApp.build` の同期的な起動例外を発生させ、Retryを連続操作してProvider生成と初期化ログを確認します。
- **推奨対応:** 起動状態を管理する専用Widgetで依存ツリーだけを再生成するか、再試行可能な初期化処理を明示的な状態機械にします。
- **今回の状態:** 修正済み。`bootstrapApplication()` はエラーフック設定後に `ApplicationBootstrap` を1回だけ `runApp` します。Statefulな起動ルートが依存セッションと世代を所有し、RetryではProviderツリーだけを破棄・再生成します。古い非同期完了と古いRetry callbackは無視され、Provider subtreeのunmount後に旧セッションを破棄します。

## RF-06: 一部のデバッグメッセージに実際の文字化けが残る

- **重要度:** 低
- **根拠:** `SettingsProvider._persistCars` のFirebase保存失敗ログに文字化けした日本語が1件残っています。READMEと既存docsはUTF-8として正常であり、エンコーディング未指定のPowerShell表示による見かけ上の文字化けとは区別して確認しました。
- **想定影響:** デバッグ時に保存失敗の内容を判読しにくくなります。リリースビルドでは `debugLog` が出力されないため、利用者への直接影響は限定的です。
- **再現条件:** オンライン状態で車両保存を失敗させ、デバッグログを確認します。
- **推奨対応:** 該当メッセージを正常な日本語または統一した英語へ置換し、ログ文言を定数化します。
- **今回の状態:** 修正済み。車両クラウド保存失敗ログを正常な日本語定数 `車両のFirebase保存に失敗しました` へ統一し、旧 `_persistCars` と文字化け文字列を削除しました。`lib` 全体に典型的な文字化け文字およびUnicode置換文字が残っていないことも確認しました。

## 確認済みの非該当事項

- `README.md` と `docs/*.md` はUTF-8として正常に読めます。既定エンコーディングでの端末表示だけを根拠にファイルを変換しないでください。
- XMLの旧形式既定値、サイズ上限、ルート要素検証は抽出後もテストで維持されています。
- AIクライアントのエラーはAPIキーやレスポンス本文を露出しない既存テストを維持しています。

## 再調査で判明した追加不具合への対応

RF-01〜06の初回修正後に、並行操作、Provider破棄、複合UIフローを含めて再調査し、次の追加対応を行いました。

- **保存状態の競合防止:** 表示設定、お気に入り、エディタ形式などの状態依存値は、操作キューで実行される時点の最新状態から算出します。初期化、CRUD、クラウド同期・読込も同じローカル直列化経路へ統合しました。直列化CoordinatorはZoneに依存せず、通常利用ではSharedPreferences単位、テスト注入時はRepositoryインスタンス単位で共有し、Retry前後や別Zoneからの操作でもlost updateを防止します。
- **不変性と破損検出:** 公開List／Mapだけでなく、車両、設定、走行ログ、表示設定が保持するネストしたJSON値も再帰的に不変化しました。v2読込は必須項目、型、日時、enum、重複ID、表示設定キーの整合まで厳密に検証し、不正データを既定値へ黙って変換しません。
- **複合操作の原子化:** AIの基準設定＋派生設定、設定保存＋ガレージ状態更新、デモ設定の一括追加を、それぞれローカル1スナップショット、通知1回、オンライン時はFirestore 1バッチで確定するAPIへ統合しました。車両CRUDも車両本体と表示設定を同じクラウドバッチで更新し、削除済み車両の表示設定が残りません。途中失敗による孤立データと再試行時の重複を防止しています。
- **クラウド処理の分離と利用者境界:** ローカル保存成功後は直ちにライブ状態へ反映して後続の端末操作を解放し、クラウド処理だけを別キューで直列化します。クラウド対象とUIDはAPI呼出時に固定し、書込み／読込みの直前・直後にUIDと実効オンライン状態を再検証するため、アカウント切替をまたいだデータ送信を防止します。利用者側の待機だけをタイムアウトさせ、基底Futureは実完了までクラウドキューの順序を保持することで、遅延した旧スナップショットが新しい同期を追い越しません。クラウド失敗は端末確定を維持した同期警告として扱います。
- **SharedPreferencesキャッシュ回復:** v2スナップショット、オンラインモード、テーマの保存が`false`または例外になった場合は`reload()`で先行更新されたメモリキャッシュを端末上の値へ戻します。回復にも失敗した場合は明示的な永続化失敗とし、同一プロセス内のRetryで未保存値を公開しません。
- **IDと大量同期:** 走行ログなどのIDを時刻精度に依存しないUUID v4へ変更しました。全件同期は冪等な書込みを最大450件のバッチへ分割し、先にupsert、後に古いドキュメント削除を行うことで、Firestoreの500書込み上限を超えず、途中失敗後の再試行で収束します。
- **起動・テーマ・認証:** Retryは旧Provider subtreeのunmountとセッション破棄完了後にだけ新しいfactoryを開始します。テーマ読込を起動セッションのawait対象にし、テーマ保存も保存成功後にだけ公開します。認証Providerの型をモード切替前後で固定し、`AuthService` の購読を破棄時にcancelすることでNavigator状態消失と破棄後通知を防止しました。
- **UIの再入防止と表示整合:** 主要な保存・削除・インポート・表示変更に処理中ガードを追加し、処理中はボタンと戻る操作を無効化しました。`false`／`null` のno-op結果では成功表示や画面遷移を行いません。同期警告は画面遷移後も橙色の警告だけが最終表示として残り、緑色の成功表示で上書きされません。オフライン時の同期ボタンを無効化し、初回同期失敗は「オンライン有効・端末保存済み」の警告として表示します。OCRを含む利用者向け通知から内部例外文字列を除去しました。

## 残存する非ブロッカーの検証範囲

- Firebase-ready／認証済みの起動分岐は、現在のオフライン専用構成では実接続スモークを行っていません。
- Firestoreのbatch API呼び出しはリポジトリ境界テストで検証していますが、実Firestoreに対するシリアライズ契約テストはありません。
- Firebaseへ送信済みのFutureはタイムアウト後に取消できません。利用者への応答と端末側の編集は継続できますが、データ逆行を避けるため後続クラウド操作は基底Futureの実完了まで順番待ちになります。完了後はUID整合確認と次回の冪等な全件同期で収束しますが、実Firebaseでのタイムアウト回復はスモーク未実施です。
- 今回の最終確認ではWebブラウザおよびAndroidエミュレータへの実起動スモークは行っていません。
- トラック検索とAI会話ダイアログは抽出前後の実装を維持していますが、ダイアログ結果だけを対象にした専用Widgetテストはありません。
