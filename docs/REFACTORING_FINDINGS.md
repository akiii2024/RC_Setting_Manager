# リファクタリング調査結果

更新日: 2026-08-12

## 方針

この文書は、全体リファクタリング中に見つかった不具合候補と運用上のリスクを記録するものです。既存挙動との互換性を優先するため、以下の項目は今回の変更では修正していません。重要度は、データ消失・ユーザー影響・発生可能性を合わせた暫定評価です。

## RF-01: オフライン固定状態と保存済みオンライン状態が一致しない

- **重要度:** 中
- **根拠:** `app/app_bootstrap.dart` は `preferredOnline = false` として常にオフライン画面を構築します。一方、`SettingsProvider` は同じ `online_mode` キーを読み込み、値が `true` ならクラウドリポジトリの生成を試みます。`AppModeProvider` と `SettingsProvider` が別々に同じ設定を管理しています。
- **想定影響:** 画面はオフラインでも `SettingsProvider.isOnlineMode` が `true` になり得ます。Firebase未初期化時の例外ログ、クラウド保存判定の不整合、オンライン機能再公開時の予期しない同期につながる可能性があります。
- **再現条件:** `SharedPreferences` の `online_mode` を `true` にした状態で現在のオフライン専用リリースを起動し、両Providerの状態を比較します。
- **推奨対応:** オンライン状態の唯一の所有者を決め、`SettingsProvider` へ明示的に注入します。オフライン専用リリースでは保存値を無効化するのか、読み込むが同期しないのかを移行仕様として決定します。
- **今回の状態:** 未修正。保存済み設定の意味を変えないため、既存の分岐を維持しています。

## RF-02: ローカル永続化失敗が呼び出し元へ伝わらない

- **重要度:** 高
- **根拠:** `SettingsProvider` の `_saveSettings`、`_saveRunLogs`、`_saveOwnedParts`、`_saveCars` などは例外をログへ出した後に正常終了します。CRUD処理は先にメモリを更新し、そのまま通知または成功値を返します。
- **想定影響:** 画面では保存済みに見えても、再起動すると変更が消える可能性があります。容量不足、ブラウザストレージ拒否、破損データなどで発生してもユーザーへ通知されません。
- **再現条件:** 書き込み時に例外を投げる `SettingsLocalRepository` を注入し、`addSetting` を実行します。追加設定はメモリに残り、メソッドも成功値を返します。この現行特性はテストで記録済みです。
- **推奨対応:** 保存結果を型で返し、UIへ失敗状態を通知します。操作単位でメモリ変更をロールバックするか、未保存キューと再試行方針を導入します。
- **今回の状態:** 未修正。公開メソッドの成功・失敗契約を変えないため、現行特性を維持しています。

## RF-03: 車両CRUDで通知とクラウド保存が重複する

- **重要度:** 中
- **根拠:** `_persistCars` がローカル保存、クラウド保存、`notifyListeners()` を実行した後、`updateCar`、`addCar`、`deleteCar` が再度クラウド保存と通知を実行します。
- **想定影響:** オンライン時に同一内容が二重送信され、Firestore使用量と待ち時間が増えます。画面も一操作で複数回再構築され、将来リスナーへ副作用を追加した場合は二重実行の原因になります。
- **再現条件:** 呼び出し回数を記録する `SettingsCloudRepository` とProviderリスナーを注入し、車両の追加・更新・削除を1回実行します。
- **推奨対応:** 永続化と通知を `_persistCars` に一本化し、公開CRUD側の重複ブロックを削除します。先に通知回数を受け入れ基準として確定します。
- **今回の状態:** 未修正。観測可能な通知回数を変えないため、レポートのみとしています。

## RF-04: 走行ログと派生セッティングの保存が一体化されていない

- **重要度:** 中
- **根拠:** `addRunLog` は変更点がある場合に先に `addSetting` を完了させ、その後で走行ログを生成・保存します。ローカル保存とクラウド保存もエンティティごとに独立しています。
- **想定影響:** 途中の保存だけが失敗すると、走行ログから参照されない派生セッティング、またはクラウド側だけ欠けた関連データが残る可能性があります。
- **再現条件:** 派生セッティング保存は成功し、走行ログ保存だけ失敗するリポジトリを使って、変更点付きの走行ログを追加します。
- **推奨対応:** 走行ログと派生セッティングを1つのユースケース結果として構築し、ローカルでは一括コミット、クラウドではバッチまたは再同期可能な処理単位にします。
- **今回の状態:** 未修正。保存順と失敗時の既存状態を変えないため、現行フローを維持しています。

## RF-05: 起動失敗時のRetryがアプリ全体を再度 `runApp` する

- **重要度:** 中
- **根拠:** 起動失敗画面のRetryは `bootstrapApplication()` を再実行し、依存Providerを作り直して `runApp` を再度呼びます。これは元の `main()` 再呼び出しを分離後も維持したものです。
- **想定影響:** 初回起動の非同期処理が残っている場合、再初期化処理と競合する可能性があります。根本原因が継続している場合は、状態を失いながら同じ失敗を繰り返します。
- **再現条件:** `MyApp.build` の同期的な起動例外を発生させ、Retryを連続操作してProvider生成と初期化ログを確認します。
- **推奨対応:** 起動状態を管理する専用Widgetで依存ツリーだけを再生成するか、再試行可能な初期化処理を明示的な状態機械にします。
- **今回の状態:** 未修正。既存のRetry動作を維持しています。

## RF-06: 一部のデバッグメッセージに実際の文字化けが残る

- **重要度:** 低
- **根拠:** `SettingsProvider._persistCars` のFirebase保存失敗ログに文字化けした日本語が1件残っています。READMEと既存docsはUTF-8として正常であり、エンコーディング未指定のPowerShell表示による見かけ上の文字化けとは区別して確認しました。
- **想定影響:** デバッグ時に保存失敗の内容を判読しにくくなります。リリースビルドでは `debugLog` が出力されないため、利用者への直接影響は限定的です。
- **再現条件:** オンライン状態で車両保存を失敗させ、デバッグログを確認します。
- **推奨対応:** 該当メッセージを正常な日本語または統一した英語へ置換し、ログ文言を定数化します。
- **今回の状態:** 未修正。不具合候補は報告のみとする方針に従っています。

## 確認済みの非該当事項

- `README.md` と `docs/*.md` はUTF-8として正常に読めます。既定エンコーディングでの端末表示だけを根拠にファイルを変換しないでください。
- XMLの旧形式既定値、サイズ上限、ルート要素検証は抽出後もテストで維持されています。
- AIクライアントのエラーはAPIキーやレスポンス本文を露出しない既存テストを維持しています。
